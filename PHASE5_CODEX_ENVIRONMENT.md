# Phase 5 Codex Environment

Inspected: 2026-08-11 (Asia/Shanghai)

## Installation and selected runtime

- CLI: `/usr/local/bin/codex`
- Version: `codex-cli 0.145.0`
- Python package `openai-codex`: not installed in either the project virtual
  environment or the system Python environment
- Selected production integration: `codex app-server` over stdio JSONL
- Rejected as the primary backend: `codex exec` (it does not expose the durable
  Thread/Turn control plane required by Phase 5)

App Server was selected because the live version exposes persistent Threads and
Turns, native JSON Schema output constraints, working-directory and sandbox
policy controls, server-initiated approvals, turn interruption, history reads,
and per-turn token usage. Installing an SDK solely to choose a different runtime
would change the user's environment and would not improve the verified control
surface.

## Live protocol findings

The schema generated by the installed CLI confirmed:

- initialization requires `initialize` followed by `initialized`
- `thread/start`, `thread/resume`, and `thread/read(includeTurns=true)`
- `turn/start` returns a durable turn id; statuses are `inProgress`,
  `completed`, `failed`, and `interrupted`
- `turn/interrupt` requires both the thread id and turn id
- `turn/start.outputSchema` accepts an arbitrary JSON Schema value
- `workspaceWrite` sandbox policy accepts explicit writable roots and a
  boolean `networkAccess` flag (default false)
- command and file-change approvals are server requests; one-time decisions are
  `accept` and `decline`
- `thread/tokenUsage/updated` includes both cumulative `total` and turn-local
  `last` token breakdowns
- `model/list` exposes model ids, defaults, and supported reasoning efforts

The generated schema was inspected from a temporary directory and is not copied
into the repository. It is version-specific and is regenerated during manual
compatibility checks.

## Safety decisions

- Every Codex turn uses the AgentRun root as `cwd`, never this source repository.
- Production configuration forbids `dangerFullAccess`.
- Network access defaults to false and is enabled only when the typed task
  permission requests it.
- Context artifacts are copied into the disposable run directory, hash checked,
  and marked read-only; the source artifact store is never mounted writable.
- Only one-turn `accept` or `decline` decisions are exposed. Session-wide or
  policy-amending approval responses are not supported.
- Real model tests are opt-in through `SARS_CODEX_INTEGRATION=1`; default pytest
  performs zero real Codex turns.

## Budgeted real integration result

The original Phase 5 budget submitted two opt-in tiny turns. Both were rejected
by the upstream structured-output schema validator before model execution and
reported no token usage:

1. Pydantic open dictionary fields required deterministic
   `additionalProperties: false` normalization.
2. Pydantic `Path` emitted unsupported `format: path` metadata.

Phase 5.1 replaced the generic normalizer with an explicit versioned wire
contract and authorized exactly one additional tiny turn. That turn passed
schema preflight, executed the model, and returned a result that passed wire,
domain, and Controller security validation. The live App Server's
`turn/completed` notification omitted items, so the bridge initially reported
`CODEX_RESULT_MISSING`; a same-thread `thread/read` recovered the final message
without another turn. The bridge now performs that hydration automatically, and
Fake recovery coverage verifies one `turn/start`.

The recovered AgentRun succeeded, but its valid semantic outcome was `blocked`:
the read-only prompt referenced the fixture file while also denying local-command
access. The Task therefore correctly became `BLOCKED`. The future tiny demo now
includes the same fixture values inline while retaining all-denied permissions,
but the one-turn Phase 5.1 budget was not exceeded to revalidate that adjustment.
Phase 6 should wait for review or a separately authorized end-to-end Task success.
